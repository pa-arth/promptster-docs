title: "Use Promptster from Claude (MCP)"
description: "Connect Claude, Cursor, or any MCP client to Promptster to run assessments and read raw session telemetry for grading."
---

To drive Promptster from an AI assistant, connect it to the Promptster MCP server. Your assistant can then list problems, create assessments, invite candidates, and read each session's raw event log and teammate conversations, without you writing API calls.

The MCP server uses the same API key and the same rules as the [REST API](/reviewers/api/authentication). Inviting candidates through it uses your plan's assessments exactly as the dashboard does.

## Connect

Create an API key in the dashboard under **Settings → API Keys**, then add the server.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http promptster-hire https://api.promptster.ai/mcp/hire \
      --header "Authorization: Bearer psk_live_..."
    ```
  </Tab>
  <Tab title="Other MCP clients">
    Add a Streamable HTTP server:

    ```json
    {
      "mcpServers": {
        "promptster-hire": {
          "type": "http",
          "url": "https://api.promptster.ai/mcp/hire",
          "headers": { "Authorization": "Bearer psk_live_..." }
        }
      }
    }
    ```
  </Tab>
</Tabs>

<Warning>
  The API key acts for your whole organization. Keep it in your MCP client's local config, not in a shared repository.
</Warning>

## Tools

Every operation in the [API reference](/reviewers/api/authentication) is a tool, plus a few for grading: teammate conversations, the grading context, and facts and judgments read separately.

| Area | Tools |
|---|---|
| Problems | `list_problems`, `get_problem`, `create_custom_problem`, `get_custom_problem`, `update_custom_problem`, `create_problem_version`, `list_problem_versions` |
| Assessments | `list_assessments`, `get_assessment`, `create_assessment`, `update_assessment`, `delete_assessment`, `get_assessment_cohort_stats` |
| Teammates | `list_teammates`, `set_teammate_behavior` |
| Candidates | `send_candidates`, `list_candidates`, `list_all_candidates`, `resend_invitation`, `revoke_candidate` |
| Sessions | `list_sessions`, `get_session`, `get_session_scores`, `get_session_artifacts`, `get_session_decisions`, `get_prompt_analytics`, `get_interview_followups`, `get_session_cohort_stats` |
| Raw telemetry | `get_session_telemetry`, `get_teammate_conversations`, `get_signed_log` |
| Grading | `get_grading_context`, `get_session_facts`, `get_promptster_judgments`, `list_files`, `get_file` |
| Organization | `list_provider_keys` |

Creating an assessment doesn't use plan quota. Each candidate you send with `send_candidates` uses one assessment, except sends to your own team's email domain. Deleting an assessment or revoking a candidate can't be undone, so those tools tell your assistant to confirm with you first.

## Grade with raw telemetry

To grade a session yourself, have your assistant read the event log with `get_session_telemetry`. It returns events oldest first, 200 per page by default. Pass the returned `nextCursor` back as `cursor` while `hasMore` is true.

Sessions often run to hundreds of events. To read one stream, pass `kinds` as a comma-separated list:

| Stream | `kinds` |
|---|---|
| What the candidate asked for | `prompt` |
| What the model did | `model_turn,ai_response,tool_intent,tool_use` |
| Code changes | `file_create,file_diff,file_delete` |
| Terminal | `command` |
| Where the candidate looked | `file_read,editor_focus,editor_edit,editor_idle,web_lookup` |
| Decisions and answers | `decision_event,question_answer` |

`get_teammate_conversations` returns the full teammate thread in one call. Each message has a `direction`: `to_persona` is the candidate writing, `from_persona` is the teammate replying.

## Facts and judgments

Every session artifact is labelled `measured` or `judged`. `get_session_facts` returns only the measured ones:

- hidden test-suite results: each test's name, pass or fail, and output, plus any screenshots the tests took
- the final diff and file tree (read any file with `get_file`)
- prompt, command, diff and tool counts, and time to first change
- the candidate agent's configuration

Token counts are on each `model_turn` event in `get_session_telemetry`. The teammate threads come from `get_teammate_conversations`.

`get_promptster_judgments` returns what a Promptster model or heuristic labelled, scored, or estimated: fluency and prompt-quality signals, key moments, work-style labels, integrity flags, the summary, follow-up questions, and cost-waste estimates.

`get_grading_context` returns what the candidate was graded against. The candidate saw the brief. They never saw the rest: your reference plan and conventions doc, teammate settings, check-in questions, and the answer key (the hidden test suite and, for ticket-flow problems, the hidden requirements and who holds each).

`get_signed_log` returns the event log with each event's signature and the one before it, plus the session's public key. The call doesn't verify anything: check the signatures and the chain yourself. Events captured without a signature carry no proof.

If your own assistant does the grading, give it the grading context and the facts, and leave the judgments out.

A prompt that works well:

```text
For each completed candidate on the "Backend Senior" assessment, read the
grading context, their session facts, their teammate conversations, and their
prompt, file_diff, and command events. Grade how they scoped the task, verified
the model's work, and used their teammates. Cite event timestamps.
```

## Errors

A tool that the API refuses returns the API's status and body. For example, inviting candidates past your plan's limit returns `403` with `"code": "quota_exceeded"` and how many assessments you've used.
